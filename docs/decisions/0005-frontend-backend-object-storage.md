# 0005 — Deployable applications, shared core, and object-storage boundaries

Status: accepted

## Context

Reality originally shipped a server-rendered FastAPI application from one
Python package. The browser migration is now complete: delivery uses a static
web application at the edge plus an independently scalable, stateless Reality
Core. Uploaded source files are immutable business evidence and must not depend
on an application container's local filesystem in production.

## Decision

Keep one repository with explicit deployable applications and one shared business
core:

```text
apps/api/                  Web/API container definition
apps/mcp/                  authenticated HTTP MCP container definition
provider-site/             public landing site and static container definition
apps/web/                  authentication/product Web application and static container definition
packages/reality-core/     Python domain, application services, adapters, migrations
infra/                     target-specific deployment definitions
```

The Python core remains a modular monolith deployed through separate Web/API and
HTTP MCP processes. API, MCP, CLI, Copilot, and workers must call the same application
services. The process split does not authorize business
logic in the web app or parallel implementations in transport layers.

The public Site is static and has no API or tenant dependency. Product Web is the only
operational presentation layer and consumes the tenant-scoped JSON API. The shared core contains no Jinja templates, static browser
assets or alternative UI mutations. Compatibility browser routes only redirect
to the frontend deployment.

PostgreSQL stores typed, tenant-scoped metadata and business records. An
S3-compatible object store holds immutable binary source artifacts. PostgreSQL
stores the artifact identity, tenant, checksum, media type, size, state, and
opaque storage key; it never stores deployment-specific object URLs.

Local development uses MinIO. Production may use AWS S3 without changing
domain or service behavior.

## Required invariants

1. Every object key is tenant-prefixed and generated by Reality.
2. Artifact content is addressed and deduplicated by SHA-256 within a tenant.
3. The object store is private; downloads are mediated by tenant-scoped backend
   services or short-lived signed URLs.
4. SourceRecord immutability and Source → Evidence → Reality remain unchanged.
5. Browser code never calculates operational truth or bypasses confirmation; Site has no application access.
6. API and MCP containers remain stateless; local artifact storage is development
   fallback only.

## Deployment shape

```text
runreality.ai      -> static public Site
www.runreality.ai  -> permanent edge redirect to runreality.ai
app.runreality.ai  -> static Product Web origin
api.runreality.ai  -> Web/API runtime
mcp.runreality.ai  -> authenticated HTTP MCP runtime at `/`

Web/API and MCP -> shared application core -> PostgreSQL
Web/API and workers -> private S3-compatible object storage
```

This topology supersedes the former mounted `/mcp/* -> Web/API origin` routing. MCP
has an independent process, public URL, probes, and connection budget but no separate
business authority or database. Web/API remains responsible for token administration
and human confirmation. MCP is HTTP-only; the frontend proxy and alternate local
compatibility path are not supported.

## Migration sequence

1. Establish physical `apps/` and `packages/reality-core/` roots. **Completed.**
2. Keep all current behavior green after the shared-core move. **Completed.**
3. Add an S3-compatible artifact adapter and MinIO development services.
4. Establish `/api/v1` and a generated TypeScript client.
5. Move pages from Jinja to the frontend incrementally. **Completed.**
6. Remove server-rendered product UI after parity. **Completed.**
7. Move authenticated MCP to its dedicated HTTP runtime and remove mounted routing.
   **Completed.**
8. Split the public Site from authentication and Product Web. **Completed.**
