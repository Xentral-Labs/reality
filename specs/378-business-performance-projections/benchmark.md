# Business projection load evidence and remaining acceptance

## Reproduction and safety
`scripts/benchmark_business_projection.py` creates its own `reality_business_bench_*` database on local PostgreSQL port 54329 and drops it afterwards. It never accepts a production database target. Test fixture cloning is restricted to that disposable database; production code uses ordinary Reality services. Run with `PYTHONPATH=packages/reality-core/src .venv/bin/python scripts/benchmark_business_projection.py --orders 10000 --tenants 3 --viewers 100 --rounds 3 --cadence 5 --output <result.json>`.

## Measured smoke trials
Hardware: Linux x86_64 managed container, five visible CPUs with cgroup quota `400000/100000` (four CPU equivalents), 16 GiB cgroup memory limit, PostgreSQL 17.11, Python 3.12.14. API pool stays at the existing default five plus five overflow connections. PostgreSQL runs in a local Docker container; storage throughput was not independently calibrated. Some trials overlap verification workloads; they are diagnostic, not isolated capacity certification.

Distribution: 10,000 sales orders in the main company and 1,000 in each of two other companies. One item/customer/location per company, roughly 90% open unreserved/overdue and 10% cancelled; cloned records are source-less. No historical shipments or correspondence and no concurrent booking producer. This intentionally does not cover duration/mail-volume throughput.

- Initial 100-viewer simultaneous burst hit the pool timeout: post-response Storyline recording requested a second connection while request sessions held the pool. The Business monitoring route is now excluded by the existing recorder exclusion mechanism. No passing latency is claimed for that failed trial.
- `benchmark-burst.json`: after the recorder fix, 300 burst requests completed; API p95 4,619.57 ms, maximum 7,095.71 ms. Main-company rebuild took 10.43 s in 51 units, unit p95 397.56 ms. This burst does not represent the frontend's phased five-second polling.
- `benchmark-smoke.json`: 100 viewers phased over five seconds, three polling rounds, 300 HTTP/ASGI requests, main company rebuild 13.72 s in 51 units. API p95 846.77 ms, maximum 1,282.90 ms. The provisional 500 ms target was **not met**.
- `benchmark-shared-loop.json`: one shared ASGI event loop, same phased workload and default pool; API median 50.20 ms and p95 783.17 ms. The provisional p95 target was **not met**. This differs from independent TestClient portals and is closer to a single API-process event loop, but still excludes real network and production authentication.

The 10,000-order trials measured reads and direct bounded rebuild compute time; they did **not** measure shared-role cadence or concurrent booking lag. Their `lag_seconds: null` is intentional.

Additional shared-role probes use three companies with 100 orders each. They perform 200 phased reads with 100 viewers, then a separate ordinary `revise_commitment` producer configured for one booking/second (nine committed revisions). No viewers run during the booking phase. The harness calls the existing scheduler/worker sweeps and spawns the actual fenced worker child for each job; no alternate queue or cache writes are used. All shared projections are warmed first; quantity changes still enqueue the other existing projections and operational-case reconciliation. Hardware is the same shared four-CPU container.

- `benchmark-shared-roles.json`: before Business enqueue preference, a deliberately restricted one-worker sweep budget (three runs/one second) left all nine changes pending after the 90-second observation timeout while 23 other shared jobs succeeded. This is a measured backlog failure, not evidence of lost bookings or successful freshness.
- `benchmark-shared-roles-prioritized.json`: Business receives the earliest timestamp among newly enqueued shared projection jobs; older FIFO work retains precedence. Scheduler sweep budget is the ordinary 100 runs/25 seconds; one worker uses ten runs/25 seconds, scheduler cadence five seconds and worker cadence one second. Read API p95 was 60.20 ms for the small fixture. All nine revisions published, with measured commit-to-observed-publication delays 7.93–19.24 seconds (p95/max 19.24 s); the provisional ten-second target was **not met**, even without simultaneous viewers. These are nine samples in a short probe, not sustained capacity certification. Configured booking rate is one/second; earlier raw records do not contain exact commit timestamps for independently calculating achieved rate.

- `benchmark-three-workers.json`: three shared workers, same small fixture and short booking phase, under concurrent verification load. All nine revisions published without errors, but delays ranged 4.00–65.11 seconds; p95/max 65.11 s. A new Business run can sit behind older jobs after its previous publication, so adding workers does not prove a ten-second bound. This probe's read p95 was 1,239.23 ms under host contention. The target was **not met**.
- `benchmark-indexed-final.json`: final finite-literal indexed cohorts, 10,000 + 1,000 + 1,000 orders, 300 phased requests/100 viewers. API median 34.81 ms, p95 **186.92 ms**, maximum 445.00 ms. The provisional API target was met in this read-only smoke fixture; concurrent booking rate was zero. Main rebuild took 13.77 s/51 direct units, unit p95 343.74 ms. Recorded PostgreSQL plans used `ix_business_order_blocked`, `ix_business_order_complete` and `ix_business_order_cancelled` (detail queries 1.144/0.020/0.346 ms respectively). These query timings exclude API/auth/transport costs; the API timings include local disabled-auth HTTP/ASGI routing.

- `benchmark-three-workers-timed.json`: repeated three-worker probe with exact UTC commit timestamps, booking durations and achieved commit rate. Nine revisions at **1.026 achieved bookings/s**, no viewers during bookings; all nine published, no worker errors. Delay range 5.77–31.03 s, p95/max **31.03 s**. This run overlapped verification and remains a short contention probe. Read p95 was 186.97 ms for the separate 100-order/company phase. The ten-second lag goal was **not met**.

The current runner records achieved commit rate and per-booking timestamps/durations; reproduce a shared-role probe with `--orders 100 --booking-rounds 3 --worker-processes 1` or `3`. Earlier probes report the configured producer rate explicitly. The million-order sustained acceptance trial below remains open. No production readiness or billion-scale claim follows from these measurements.

## One-million-order and active-company trial plan
Use a disposable PostgreSQL instance; record physical CPU model/count/quota, memory, storage IOPS/latency, PostgreSQL settings/version, API/worker replica counts, pool sizes and code commit. Repeat with warm/cold caches and isolated host resources. Initial requested dataset: 1,000,000 orders in one company plus four simultaneously active companies with 100,000 orders each. Use 10,000 items, 50,000 partners, 20 locations, one to ten lines/order, realistic partial/completed/cancelled mix (70% complete, 5% cancelled, 25% open) plus a deliberately skewed hot-item/high-open-order scenario. Seed matching source dates, corrected movements, reservations/releases, holds, revisions and message threads (at least one million messages; long-thread outliers).

Drive ordinary confirmed business services, never projection writes, at explicitly reported 1, 5, 20 and 50 committed bookings/second across the active companies (including reservation/shipment/correction/quantity/cancellation/mail/ack/reply and hot-item stock/block changes). Run the existing scheduler at five seconds and the existing worker roles, first one worker then three; no private subsystem timer or queue. Record events' commit times and poll `processing.processed_event_sequence`, `target_event_sequence`, `lag_seconds`, state and clock due moments. Measure commit-to-publication and clock-boundary-to-publication p50/p95/max, queue depth, failures/retries, per-tenant starvation and resource use for at least 30 minutes after warmup, then at least one hour of concurrent full rebuild plus bookings.

Run 100 viewers at the existing five-second polling rate with realistic phases (20 requests/s), plus an explicit synchronized-refresh burst. Exercise all filtered cohorts, first/late keyset pages, old-generation cursor expiry and mail history/Inspector reads. Collect actual HTTP p50/p95/max and failure rate, response sizes, SQL plans/buffers/rows, database/index/cache sizes and worker chunk timings. Normal-load provisional acceptance is API p95 <500 ms and processing lag <10 s; separately identify backlog/rebuild and high-fan-out results instead of hiding them in averages.

At stable quiescent checkpoints compare the unchanged full reference with every projected counter and complete cohort. During the run inject duplicate/delayed events, worker termination/restart and rollback; rebuild from no caches and concurrently from a retained published generation. After draining, require zero missing changes, duplicated contributions or cohort discrepancies. Archive input distributions, rates, raw samples and query plans together with summary statistics.

## Known capacity/consistency limits
A 200-order chunk bounds entities, not an order's line count, a message's entire reply history, or the canonical stock reader's item movement history. High-fan-out stock/partner changes and million-order rebuilds can require thousands of shared scheduler rounds and exceed ten seconds. Ancillary inventory/replenishment readers retain full existing semantics and can dominate worker time; other shared projections also compete for worker capacity. The API captures counters/details/metadata in one statement snapshot; live cohort membership can still change between separate page requests. Old generations are cleaned in bounded continuation work. These are explicit limits to validate and tune, not evidence of million-order sustained throughput.
