# Operational case candidates beyond the initial Shopify slice

**Status**: Planning backlog, not enabled runtime policies or approved schema expansion.
**Inspected**: 2026-10-05; resource/event catalogs and existing domain/services.

## Common boundary rule

A case is an independently ownable outstanding goal. Accepted facts alone do not create work. New intent/open obligations create or match a case; progress events update it; already completed facts settle matching work or remain evidence. Select owned work explicitly; related goals are not recursively transferred. A low-stock or discrepancy observation alone does not automatically authorize purchasing, adjustment or payment.

Case policies should be extensible by kind, typed anchor/resolver, trigger classification, owned actions, related impacts, completion predicate, action applicability and capability/authority requirements. The initial feature remains a closed three-family policy set. Each additional family needs its own reviewed requirements, typed links, canonical-entrypoint inventory and acceptance tests; adding a catalog row never enables execution. No generic object-ID bucket or arbitrary workflow graph is required now.

## No-case baseline

Creating/editing party, item, location, price terms or source configuration creates no case solely because data changed. Accepted completed payment/receipt/stock-count evidence likewise creates no pending execution request. New changes still trigger reevaluation of existing applicable goals and action prerequisites. A consciously commissioned data-cleanup project may have its own explicit goal later, without one case per field edit.

## Recommended expansion order

1. Finish safe initial fulfillment/return layer and resolve replacement/unannounced-return anchor gaps before enabling those automated paths.
2. Add supplier-order fulfillment using existing purchase-order/commitment roots; keep receipt progress within the procurement case.
3. Add independently ownable invoice-review and stock-block disposition goals where actual operations require them.
4. Specify replenishment, supplier returns, payment transport, collection and internal task intent roots only when their execution is adopted.
5. Defer manufacturing until its underlying authoritative business model exists.

## Separation examples

- Customer order A needs goods from supplier order P, which also serves B: A depends on P's receipt. Human takeover of A stops owned A work, not procurement for B. P is reevaluated against actual selected demand.
- Supplier order P receives 3 of 5: same procurement case remains open for 2; no separate case for each ordinary receipt. A wrong-goods complaint can become independently owned linked work if repair requires separate follow-up.
- Supplier invoice I is disputed: invoice-review/payment prerequisites change. Goods already received remain historical facts and P is not reopened simply because money is disputed.
- Stock block Q affects many orders: Q owns the release/scrap decision; dependent order plans are rechecked for availability, without copying stock state onto cases.
