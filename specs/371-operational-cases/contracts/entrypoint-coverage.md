## Method and scope

Reviewed executable command/MCP bindings, application preparation/execution, manual Web and CLI paths, Shopify/file intake, dynamic effect invocation, batch agent acceptance and worker dispatch. A Python AST call-site scan supplements textual reads; named direct calls alone cannot discover registry/getattr dispatch. Limit enforcement to adopted Shopify-related fulfillment/return/refund policy families; unrelated Finance, inventory and supplier work is not blanket-gated.

The approved implementation now supplies the described `Ensure` and `Guard` boundaries through shared producer leaves, exact proposal execution and reviewed intake application. Existing membership/tenant/domain/review checks remain mandatory. Preserve `_commit=False` flows so accepted goals and their case commit together.

## Findings and dispositions

1. **Canonical case controls implemented:** accepted commitment/announcement leaves ensure atomically; server-context guards protect actual scoped effects and generic claims. Direct lower-write tests supplement inherited adapter routing; source/preparation paths remain non-accepting.
2. **Documentless customer commitments exist:** core.create_commitment accepts absent document IDs. customer_exchanges.record_customer_exchange creates a replacement promise without an order document. Initial order-anchor policy cannot silently absorb these. Implemented disposition: allow authorized existing human workflows, report unsupported case coverage and refuse adopted automatic execution on unanchored promises. A separate reviewed anchor extension is required before automating them; do not invent an order.
3. **Unannounced returns exist:** record_movement accepts absent return_announcement_id; record_packaged_execution and return disposition can act on actual return movements. Initial announcement-anchor policy lacks a root for these. Implemented disposition: preserve human/evidence capture and explicitly block unanchored automated return work until a movement-rooted return policy is separately designed. Events alone cannot solve this.
4. **Refund bookkeeping is implemented; payout-intent transport is not:** post_customer_refund settles credit and records ledger/evidence via record_customer_refund. A proposed customer_refund_post operation is an intention to book financial effects, not proof of a pending Shopify payout request. No suitable standalone provider-refund-intent root was found in the inspected paths. Keep execution case capability unavailable; accepted refund evidence only reconciles known supported goals.
5. **Combined deliveries span goals:** outbound plans select multiple commitments. Bind every affected order case and reject automatic combined work if any required case is human-controlled.
6. **Durable execution claim is separate from effects:** generic proposal execution commits executing before handlers. Takeover cannot erase this state. Intake and Finance have special branches and must not be omitted from guard inventory.
7. **Raw/evidence/intent are distinct ingress classes:** case identity must not be generated simply from source ingestion or document recording. Ensure roots only after relevant commitments/announcements are actually accepted.
8. **No live Shopify provider boundary currently found:** future API dispatch and uncertain-result reconciliation remain a separate adapter feature. Current internal shipment execution is not proof of real provider cancellation or delivery.
9. **Demo, kits and inventory callers share leaves:** classify using actual movement/commitment context and adopted scope, not function name alone. Demo profile/synthetic callers do not imply live authority; opening/count/stock-block movements and supplier commitments create no initial Shopify cases.

## Enabling gate and planned proofs

Every enabled E-row and reachable adapter path requires a new case-layer proof in `test_case_entrypoint_coverage.py` (with detailed race tests in the planned guard/control suites). Cover atomic acceptance rollback, direct lower-level invocation, dynamic intake, batch children, absent/forged case IDs, human repair, mixed cases, stale source, lag and claim races. Unsupported goal roots must remain unavailable; their existence must not stop authorized human evidence/repair paths. Do not mark runtime coverage complete from this static inventory.
