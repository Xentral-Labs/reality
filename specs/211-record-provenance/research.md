# Research

- Decision: reuse the origin shape the Facts register already returns (`{system, type, external_id}`), extended with system name, version and received time. Rationale: a second origin shape would fork the vocabulary between the Inspector and the workspace. Alternative rejected: a register-specific summary string, which cannot be inspected or linked.
- Decision: resolve origin from `source_record_id`, which already exists on Party, Item, Location, Document, Commitment, Shipment, ShipmentPackage, ShipmentEvent, Movement, ReturnAnnouncement, LedgerEntry, Fact and BusinessEvent. Rationale: the chain is complete; only presentation is missing. Alternative rejected: a provenance table duplicating links that already exist, which Principle II forbids.
- Decision: join `SourceRecord.source_system` to `SourceSystem.code` within the tenant. Rationale: the source record keeps a textual snapshot on purpose, because evidence is immutable; the configured system is mutable. A missing match is a supported display state. Alternative rejected: adding a foreign key from source records to configured systems, which would make evidence depend on later configuration.
- Decision: the external base address lives on `SourceSystem`. Rationale: the user's explicit decision on 2026-09-16, and one installed instance has exactly one external address. Alternative rejected: an address per `SourceCapability`, which multiplies configuration without a proven case where one instance answers at two hosts.
- Decision: the vendor-specific part of the address lives in `connector_catalog.yaml` as a relative template per source type. Rationale: it is vendor knowledge, identical for every tenant, and must stay updatable centrally. Alternative rejected: copying the template onto `SourceCapability` at installation, which freezes it at install time and silently rots when a vendor changes its address shape.
- Decision: record the connector shell on `SourceSystem` and make it the only association between an instance and a connector. Rationale: `connector_shells` identifies a vendor instance by `system.description.startswith(f"{shell['name']} ")`. That description is written at installation and never updated, so the weakness is not user editing — it is that the test is a prefix test over catalog display names. With the present catalog, an instance installed from `shopify_payments` carries the description `"Shopify Payments Payments source definition · no connection"`, which satisfies the test for both `shopify_payments` and `shopify`. One instance therefore already belongs to two shells, and an address resolved through that association would point a payment record at a Shopify order path. The column resolves a present defect; addressing is the beneficiary, not the justification. Alternatives rejected: matching on code equality alone, which cannot serve `shopify_de` or `shopify_b2b`, both named as the normal case in `docs/features/source_ingestion.md`; and prefix-matching the instance code, which `docs/features/source_ingestion.md` rules out with "No fuzzy column guessing is performed".
- Decision: backfill `connector_code` once in the migration, then read only the column. Rules: an instance code equal to a connector code resolves to that connector; otherwise the description prefix resolves it, evaluated longest catalog name first and accepted only on a single match; anything else stays null. Rationale: this applies the rule that is in force today, exactly once, at a point where the result can be audited, instead of evaluating it on every read forever. A null means no shell grouping and no link — the state hand-created systems already have. Alternative rejected: keeping the inference alongside the column, which leaves two answers to one question.
- Decision: a user-entered full address template per source system, in place of catalog templates and the connector column, was considered and rejected. Rationale: one instance serves several source types whose vendor paths are not uniform — a HubSpot contact is `/record/0-1/{id}` and a deal `/record/0-3/{id}` — so it degrades into one template per capability, typed again by every tenant. Vendor knowledge belongs in the catalog. A per-capability override remains available later if a tenant proves it is needed.
- Decision: template inputs are restricted to `source_type` and `external_id`. Rationale: determinism and containment — payload fields would make the resulting address depend on data the tenant does not control and would carry payload content into an outbound address. Alternative rejected: a general payload expression language.
- Decision: a per-record `external_url` supplied by an interpreter is deferred, not designed away. Rationale: it is genuine evidence when a payload carries a canonical address, but it is immutable with the record version and therefore ages badly; the template must be primary before the exception is added.
- Decision: field-level provenance is deferred to its own specification. Rationale: "this address came from HubSpot" is an assertion about a Fact, and Facts already carry `source_record_id`; the presentation question there is a field-level affordance, not a record badge.
- Decision: display the retained payload in the inspection. Rationale: existing explain reads already return `source_payload`, so this exposes nothing new; the bound and the truncation notice are the new requirement.
- Open question deferred by design: whether contributing-source disclosure (FR-011) should also appear on aggregate rows. It should not, until an aggregate exists whose origin a user has asked for.

## Measured context
- `tests/test_application_catalog.py` pins `len(catalog.discovered_operations) == 486` at planning time; each new public service function must be classified and the count moved in the same branch.
- `InterpretationRecordReference` is uniquely keyed on `(tenant_id, outcome_id, record_type, record_id)`. A reverse lookup by `(record_type, record_id)` has no supporting index. This feature does not use that direction — it resolves through `source_record_id` — and any later use must add the index first.
